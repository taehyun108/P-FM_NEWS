01 — 구성무엇이 어디서 돌고 있나

파이썬 파일 backend/main.py 하나(약 6,100줄)가 API 서버·수집 루프· 텔레그램 봇·주간 레포트를 모두 담고 있다. 프런트엔드는 프레임워크 없는 바닐라 JS 3파일이고, 데이터는 로컬 SQLite 파일 하나에 들어간다.

프런트엔드

파일줄역할
index.html298뼈대 마크업, 마스터 패널 모달, 주간동향 패널
app.js1,160전체 로직 — 프레임워크·빌드 없음
style.css465딥네이비 테마, 3열 포토카드 그리드

상태는 state 객체 하나(필터·검색·페이지)에 모으고 URL 쿼리스트링과 동기화한다 — ?page=까지 넣어 새로고침·링크 공유 시 페이지가 유지된다. 목록은 페이지당 9개 포토카드로 끊어 페이지 번호 네비게이션으로 넘긴다(무한 스크롤 아님). 브라우저 저장소는 localStorage만 쓴다 — 즐겨찾기 목록, 마스터 토큰, 필터 접힘 상태. 서버로는 가지 않는다. 헤더의 탭은 전체 기사 · 즐겨찾기 · 주간동향 셋이 서로 배타적으로 전환된다.

목록 정렬은 최신순(기본, 발행일 내림차순)과 중요도순 (?sort=score) 중 하나를 필터 영역에서 고른다. 중요도순은 사용자가 URL로 직접 등록한 기사(source_type='manual')를 먼저 올리고, 그다음 중요도 점수·발행일 순이다 — 직접 고른 기사가 최신 자동수집분에 묻히지 않게 한다. 직접 등록한 기사 카드에는 「✍ 직접 등록」 배지가 붙고, URL 등록 미리보기에는 “이 기사가 맞습니까?” 제목 확인줄을 띄워 엉뚱한 링크 등록을 막는다.

백엔드 — 약 6,100줄

설정 → 저장소 계층 → 시드 → URL 정규화 → HTTP → 수집 → 본문추출 → 분류·중요도 → LLM → 중복판정 → 파이프라인 → 시세 → 텔레그램 봇 → 주간 레포트 → API → CLI 순으로 배치돼 있다. 저장소는 Storage 추상 클래스 아래 SqliteStorage와 SupabaseStorage 두 구현이 있어, .env의 DB_BACKEND 한 줄로 전환된다.

02 — 수집기사가 통과해야 하는 7개 게이트

게이트는 싼 판정을 앞에, 비싼 판정을 뒤에 두도록 순서가 정해져 있다. G0–G2.5는 네트워크를 쓰지 않아 비용이 0이고, HTTP 요청은 G3부터, 과금은 G6에서만 발생한다. 아래 숫자는 실제 1회 실행 로그다.

중복 판정 4단계

같은 사건을 여러 매체가 전재하므로 4단계로 묶는다. 앞 단계에서 확정되면 뒤로 안 넘긴다 — 임베딩(4단계)은 비용이 요약 단계를 넘어설 수 있어 1회 실행당 30회로 막아 두었다.

단계판정임계비용
1정규화 URL 완전 일치—DB 조회
2본문 SHA-256 해시 일치—DB 조회
3제목 유사도 AND 발행시각 24시간 이내0.90로컬 계산
4제목 임베딩 코사인 유사도0.92OpenAI 과금

3단계에서 유사도가 0.62–0.90 사이인 "잔여 후보"만 4단계로 보낸다. 중복으로 판정되면 새 URL을 별칭으로 누적하고, 새 기사의 언론사 등급이 더 높으면 카드의 표시 정보(제목·링크·언론사·기자·썸네일)를 그쪽으로 승격한다. 요약·SWOT 등 분석 결과는 같은 사건이므로 그대로 두고, 피드가 재정렬되지 않도록 발행시각도 유지한다.

목록 API는 원래 527 ms였다. list_articles가 a.*로 title_embedding(행당 약 31 KB, 합계 5.8 MB)까지 읽고 있었는데, 카드에는 쓰이지도 않는 값이었다. 필요한 컬럼만 고르도록 바꿔 15배 빨라졌다(36 ms).

그 뒤로도 /api/articles는 캐시가 없어 필터 클릭·페이지 이동마다 3,000행 조인 조회 + 행마다 card_tags(그룹사 규칙 매칭·정규화)를 다시 돌았다. 데이터는 수집 주기(기본 300초)에 한 번만 바뀌므로 (기간, 검색어)별 스캔·태그 결과를 15초 캐시하고, 필터링·페이지네이션·카드 생성만 매 요청 수행하도록 바꿨다. /api/filters도 같은 캐시를 공유한다. 웜 응답 기준 다시 7배(36 → 5 ms). 수동 등록·draft 확정 시에는 캐시를 즉시 비운다.

SQLite 커넥션은 synchronous=NORMAL(WAL에서 앱 크래시에 안전) · busy_timeout=5000 · temp_store=MEMORY · cache_size≈16 MB로 연다. 파이프라인이 문장마다 커밋하므로 fsync 부담이 컸는데, 커밋 지연과 WAL 비대화가 함께 줄었다. 그룹사 별칭·정책/시황/카테고리 키워드의 소문자 변환은 모듈 로드 시 1회만 하도록 사전계산했다(detect_group_companies·score_article·detect_categories가 호출마다 리스트를 다시 만들던 것을 제거 — 파이프라인·API 공통 경로).

일회성 정리 명령

규칙을 바꿨을 때 기존 데이터에 소급 적용하는 CLI가 준비돼 있다. fixcategories(재태깅) · fixgroups(그룹사 보강) · regroup(원문 리드로 그룹사 재판정) · fixpress(언론사명) · fixofftopic(무관 기사 보관) · reanalyze(끊긴 분석 복구) · reswot(SWOT 재생성) · fixlinks · fixdates. weekly [--dry]는 주간 레포트를 즉시 생성·발송한다.

부트스트랩 억제. 첫 실행 시각을 기록해 두고, 그 이전에 발행된 기사는 절대 알림하지 않는다. 파이프라인이 오래 멈췄다 재개될 때 과거 기사가 한꺼번에 발송되는 것을 막는다.

08 — 주간 레포트월요일 아침 이메일

한 주치 기사를 계열사·주제별로 모아 LLM이 주간 종합 SWOT과 포스코 그룹 영향 분석을 합성한다. 결과는 weekly_reports에 저장하고, 같은 HTML을 이메일과 웹 주간동향 탭이 함께 쓴다.

Gmail은 앱 비밀번호로. SMTP_USER와 앱 비밀번호는 같은 Google 계정이어야 한다. 회사 계정이 앱 비밀번호를 막으면 개인 @gmail.com을 발신자로 두고 회사 주소를 수신자로 넣는다. SWOT 4분면은 강점(초록)·약점(주황)·기회(파랑)· 위협(빨강)으로 색을 나눠 이메일에서도 한눈에 구분된다.

09 — 대외협력마감일이 1순위인 화면

입법·행정예고 의견제출은 기한이 지나면 기회 자체가 사라진다. 그래서 이 탭의 기본 정렬은 의견제출 마감일 임박순이고, D-7 이내 항목은 패널 최상단에 배너로 따로 띄운다. 필요하면 정렬 드롭다운에서 최신순(공고 시작일) 이나 영향도순(?sort=recent|impact)으로 바꿀 수 있다. 뉴스 탭과 목적이 달라 데이터·수집기·화면을 모두 분리했다.

부처 필터는 실제 수집된 항목의 소관만 보여준다(전체 시드 32개가 아님). 국민참여입법센터·국회 목록을 전 부처 대상으로 크롤한 뒤 관련성 게이트(G2.5)에서 산업 키워드가 없는 일반 행정·조세·소비자 규정을 걸러내므로, 산업통상부·기재부라도 이차전지·철강·통상과 무관한 공고는 목록에 남지 않는다. 부처명은 매핑된 이름이 없으면 크롤 원문(agency_raw)을 그대로 필터 값으로 쓴다 — 2025 정부조직 개편으로 바뀐 신 명칭(산업통상부·재정경제부·행정안전부 등)도 필터에 노출된다.

격리 설계

로직은 전부 신규 3파일(external_affairs.py 1,014줄 · external_affairs.js · external_affairs.css)에 있고, 기존 파일에는 연결선만 그었다 — main.py 11줄, app.js 4줄, index.html 2곳, style.css 0줄. 모든 CSS 클래스는 .ea- 접두사이고, URL 파라미터도 ea_page처럼 접두사를 붙여 기존 필터 상태와 섞이지 않는다.

external_affairs.py는 main.py를 import 하지 않는다. 순환 참조를 만들지 않으려고 now_utc·iso·jload 같은 3~5줄 유틸은 복제했다. DB도 Storage 클래스에 손대지 않고 스레드 전용 커넥션을 새로 연다. 기존 url_ledger·keyword_sets는 읽기만 하고, 쓰기는 ea_url_ledger에만 한다.

게이트와 분석

뉴스와 같은 순서(G0 실행내중복 → G1 메모리캐시 → G2 DB대조 → G2.5 관련성)로 거르고, HTTP·LLM 은 G2.5 통과분에만 쓴다. 법제처에는 전 부처의 모든 법령이 올라오므로 G2.5 가 특히 중요하다 — 관심 부처 18곳이거나 이차전지·철강·환경·통상 관련어가 걸릴 때만 통과시키고, 나머지는 ea_url_ledger에 기록해 다음 주기에 다시 받지 않는다.

영향도
high/medium/low/none. 근거 조문을 인용하지 못하면 코드가 강제로 none으로 내린다 — LLM 이 근거 없이 높은 영향도를 주장하는 것을 신뢰하지 않는다.
본문
저장하지 않는다. G2.5 통과분만 상세(REST 또는 상세 페이지 크롤)를 받아 제안이유·주요내용을 메모리로 넘겨 그 회차에 분석하고 버린다 (기존 §7-3 최소 보관과 동일).
LLM 예산
전용 일일 상한 EA_LLM_DAILY_LIMIT(기본 50). 전체 상한과 작은 쪽을 쓰되, 초과 시 대외협력만 멈추고 뉴스 분석은 계속된다. LangSmith 태그 external_affairs로 비용을 따로 본다.
알림
만들지 않았다. ea_policy_items는 articles가 아니므로 구조적으로 기존 알림 큐에 들어갈 수 없다. category 값만 채워 두어, 나중에 마스터 패널 토글 하나로 붙일 수 있게 했다.
법적 표기. 정부 공개자료라도 본문 전문은 게시하지 않고 요약 + 원문 링크만 둔다. 패널 하단에 "AI 생성 분석이며 법률 자문이 아님"을 상시 표시한다.
