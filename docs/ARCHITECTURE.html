게이트는 싼 판정을 앞에, 비싼 판정을 뒤에 두도록 순서가 정해져 있다. G0–G2.5는 네트워크를 쓰지 않아 비용이 0이고, HTTP 요청은 G3부터, 과금은 G6에서만 발생한다. 아래 숫자는 실제 1회 실행 로그다.

03 — 관련성포스코가 안 나와도 남기는 세 갈래

기본 규칙은 "제목·스니펫·본문 어디에도 포스코·계열사가 없으면 버린다"이다. 그런데 정부 정책·해외 통상 조치·배터리 생태계 뉴스는 회사명이 안 나와도 대외협력·소재사업에 직결된다. 그래서 세 갈래의 예외를 뒀다.

네이버 수집 1차 필터(제목 전용)가 관련 기사를 통째로 버리던 문제 (2026-09-10 수정). _naver_item_relevant() 는 네이버 API 가 준 제목만 보고 "이 기사를 아예 받을지" 를 정한다(본문은 아직 안 받은 상태). 여기서 탈락하면 뒤의 배터리·통상 예외 규칙(위 세 갈래)까지 갈 기회조차 없다. 실제 누락 사례 두 건으로 원인을 확정했다:
  • "금양, 기장공장을 데이터센터로 물적분할…" — 제목에 '배터리'가 없고 금양이 배터리 회사 목록에 없어서 탈락. 본문은 배터리 사업 얘기였다.
  • "산업장관, EU 산업가속화법 우려 전달…" — 산업가속화법(2025~2026 EU 신규 산업·탈탄소 입법)이 TRADE_MEASURE_KW 에 없어 통상 조치로 인식되지 않았다.
대응: ① TRADE_MEASURE_KW·BATTERY_SCOPE_KW 에 신규 항목 보강. ② 회사명·통상 조치명 같은 고정밀 신호는 제목이 아니라 리드(스니펫)에 있어도 인정 하도록 _naver_item_relevant()·_title_snippet_relevant() 를 확장 — 단 '배터리'·'통상' 같은 일반어는 여전히 제목에만 있어야 인정한다(느슨하게 풀면 네이버 검색 블러브 특유의 무관 기사가 대거 유입된다). ③ 금양처럼 지명(금양읍)과 겹치는 짧은 회사명은 battery_company_hit() 가 지명 형태로만 나오면 회사 언급으로 안 본다.
SPA(<script> JSON) 본문 추출 실패로 news1.kr 기사가 전부 무관 처리되던 문제 (2026-09-10 수정). news1.kr 은 본문 문단을 <script> 안 {"type":"text","content":"..."} JSON 배열로 넣는다. 본문 추출 1순위인 readability, 그 폴백인 BeautifulSoup 둘 다 <script> 를 걷어내므로 내비게이션·저작권 문구 수백 자만 남고 실제 본문(그 안에 '포스코퓨처엠' 이 있어도)은 통째로 사라졌다 — 이 언론사 기사 전체에 영향을 준 버그였다. extract_body() 가 이제 '"type":"text"' 문자열이 있으면 _json_script_body() 로 그 문단들을 이어붙이고, readability 결과보다 길면 그쪽을 채택한다(다른 사이트는 이 문자열이 없어 비용 0).

대시보드 — 발송 추적

통계 바의 분석 대기 · 발송 실패 카드를 누르면 해당 기사가 피드와 똑같은 포토카드로 펼쳐진다(/api/stats/analysis-pending·/api/stats/notify-failed 가 build_card 결과를 그대로 반환). 발송 실패 카드는 위에 텔레그램이 돌려준 실제 원인(예: Too Many Requests: retry after 577)이 붙는다.
발송 로그 카드(발송 실패 오른쪽)는 봇으로 실제 나간 메시지 전문과 발송 이유를 보여 준다. _telegram_send() 한 곳에서 성공·실패 가리지 않고 telegram_log 에 적재하며(로그 실패는 발송에 영향 없음), 30일 후 정리된다. 발송 이유는 보내는 시점에 제목·판정 그룹사·점수로 다시 따져 사람이 읽을 문구로 남긴다 — 항상발송 키워드 '포스코퓨처엠' · 무조건 발송 점수 66 ≥ 65 · 중요도 55 ≥ 임계값 30, 수동 등록이면 앞에 URL 등록 · . 그 밖에 직접 전송(카드의 ↗) · 봇 응답 · 연결 테스트.

텔레그램 rate limit · flood 대응

텔레그램은 한 채널에 분당 약 20건이 한도이고, 넘으면 429 Too Many Requests: retry after N 으로 봇 전체를 N초간 막는다. 이 상태에서 계속 요청하면 금지 시간이 오히려 늘어난다(2026-09-08, 억제 해제 후 27건/분이 한꺼번에 나가 4건이 영구 실패한 사고). 대응: ① _rate_gate() 가 최근 60초 발송을 TG_MAX_PER_MIN(17) 아래로 유지, ② _telegram_send() 가 429의 retry_after 를 파싱해 _flood_arm() 으로 그만큼 봇 전체 발송을 보류, ③ _send_notifications() 는 flood 중이면 그 회차를 건너뛰고 배치 도중 429 를 만나면 즉시 중단, ④ rate limit·5xx·네트워크 오류는 재시도 횟수를 깎지 않음(일시 장애로 영구 실패 방지) — 단 NOTIFY_MAX_AGE_HOURS(24) 초과 시 포기하고 failed, ⑤ 발송 간격 RATE_LIMIT_SLEEP 3.5초, 회차당 SEND_BATCH_PER_CYCLE 12건. 막힌 실패 건은 python backend/main.py retryfailed 로 큐에 되돌린다.

카카오톡 '나에게 보내기' 병행 발송 (선택 · 기본 비활성)

현재는 꺼져 있다. 카카오 text 템플릿이 200자 한도라 텔레그램(4096자) 대비 요약·관점을 다 못 담아, 텔레그램만으로 운영한다. 코드·라우트·selftest 는 그대로 남아 있고 KAKAO_ENABLED=true + REST 키 + kakao-auth 1회면 다시 켜진다 (Config.kakao_feature_enabled → kakao_configured 게이트).
켰을 때 동작: .env 에 KAKAO_REST_API_KEY·KAKAO_CLIENT_SECRET· KAKAO_REDIRECT_URI 를 채우고 최초 토큰을 1회 발급하면, 텔레그램으로 나가는 같은 기사가 텔레그램과 같은 서식(태그·제목·요약·포스코 관점:)으로 카카오톡 나와의 채팅에도 전송된다 (_send_one() 안에서 _telegram_send 직후 _kakao_send(row=row) 호출 → _kakao_text_from_row()). 카카오 text 템플릿을 쓴다 — PC 카카오톡에서도 일반 메시지처럼 펼쳐 보이지만 200자 한도라 제목+요약을 우선 채우고 남는 만큼만 관점을 붙인다(_clip() 로 … 처리). 링크는 본문이 아니라 link 필드·원문 보기 버튼으로 뺀다. feed 카드는 PC 에서 2줄로 접히고 "모바일에서 확인" 이 붙어 쓰지 않는다. 연결 테스트·콜백 등 row 가 없을 때만 제목+링크 text. 봇 토큰이 없어 사용자 OAuth(scope talk_message)를 쓴다 — refresh_token(약 60일)·access_token(약 12시간)을 run_state 에 저장하고, access token 만료 시 _kakao_access_token() 이 refresh 로 자동 갱신한다.
최초 토큰 발급. 서버를 켠 상태에서 python backend/main.py kakao-auth 가 출력하는 카카오 동의 URL 을 브라우저에서 한 번 연다 → 동의하면 카카오가 GET /kakao/callback?code=… 로 돌려보내고, 이 FastAPI 라우트가 코드를 토큰으로 교환해 저장한 뒤 "카카오 연결 완료" 페이지를 보여 준다(수동 복사·붙여넣기 불필요). 리다이렉트 URI 는 카카오 콘솔 '카카오 로그인 > Redirect URI' 에 똑같이 등록해야 한다 (로컬 http://localhost:8000/kakao/callback, 배포 시 https://<배포주소>/kakao/callback).
발송 결과는 텔레그램과 같은 telegram_log 에 kind 뒤에 (카카오) 를 붙여 기록한다. 마스터 패널 알림 채널의 카카오 토글(kakao_enabled)로 끌 수 있고, 토큰이 없으면 토글은 비활성으로 표시된다.

Supabase 전환 — 완료 (2026-09-09)

운영 DB 를 Supabase 로 옮겼다. SQLite 2,600행을 migrate 로 배치 이관 → DB_BACKEND=supabase → 서버 재시작. 파이프라인 1사이클 149초(SQLite 40~70초 → 네트워크 왕복이 더해졌지만 주기 300초 안). 이관 절차: ① SQL Editor 에서 schema.sql 실행 ② DB_BACKEND=supabase ③ python backend/main.py migrate ④ 재시작. (schema.sql 이 19개 테이블 전부에 RLS 를 켜므로 SQL Editor 의 "Run and enable RLS" 자동 재작성은 쓰지 않는다 — 그게 CREATE TABLE 을 깬다.)

SQLite 에선 안 보이던 것들이 이관 후 첫 사이클에 터졌다.
  • PostgREST max-rows(1000) — .limit(40000) 이 조용히 1000 으로 잘려 period=all 이 1,000건만 보였다. _page(factory, cap) 로 Range 헤더 페이징.
  • .in_(...) URL 길이 초과 — 구글뉴스 리다이렉트 URL 400개를 쿼리스트링에 넣어 Bad Request. _in_batches 로 누적 4KB 씩 분할.
  • HTTP 팬아웃 → 연결 끊김 — bump_ledger 가 URL 마다 select+update 를 순차로(회당 1,000+회) 쳐 HTTP/2 가 죽었다. 배치 조회 + 한 번의 upsert 로. alias 확인도 URL 마다 contains 쿼리 대신 alias 붙은 극소수 행만 통째로 훑는다.
  • collection_logs.id bigserial 충돌 — 이관이 명시 id 를 넣어 시퀀스가 안 움직였다. migrate 가 bigserial 테이블은 id 를 빼고 넣도록 수정.

이관 전 점검에서 미리 고친 것: telegram_log 를 _MIGRATE_TABLES 에 추가, purge_old_articles 의 notifications 전체 조회(limit 100000) → 후보 id 만 in_() 청크 조회(9개월 뒤 오삭제 방지), 그리고 아래 스캔 스토어.

운영 기준 시간대 — 배포하면 반드시 맞춰야 한다

야간 억제(23–07시) · 주간 레포트 발송 시각 · 대외협력 수집 시각(9·15시) 세 가지는 한국 시간으로 판단해야 한다. 로컬 PC 는 KST 라 datetime.now() 로도 맞았지만, 클라우드 서버는 대부분 UTC 로 돈다 — 그대로 두면 9시간이 어긋나 야간 억제가 대낮에 걸리고 주간 레포트가 일요일 밤에 나간다. 그래서 now_local()(main) · now_local()(external_affairs) 이 APP_TZ_OFFSET(기본 9) 을 적용한 시각을 돌려주고, 세 판정이 모두 이 함수를 쓴다. 저장·비교용 시각은 지금까지처럼 전부 UTC(now_utc()·iso())다 — 지역시간은 스케줄 판단에만 쓴다.
야간 억제 창(시작·종료 시각·최소 점수)은 마스터 패널 3번에서 조정한다 — effective_night(ctx) 가 run_state(마스터) 값을 우선하고, 없으면 .env(NIGHT_START_HOUR·NIGHT_END_HOUR·NIGHT_MIN_SCORE, 기본 23·7·80). 시각은 서울시간. _in_night_window(hour, start, end) 가 start>end 면 자정을 넘는 창(23·0·1·…·6시)으로, start<end 면 낮 창으로 해석한다. 최소 점수를 101 로 두면 야간엔 '무조건 받을 키워드'에 걸린 기사만 나가고 나머지는 아침에 나간다.
Supabase 는 run_state 에 night_start_hour·night_end_hour·night_min_score 컬럼이 필요하다(schema.sql 반영 · 기존 프로젝트는 alter table 1회).

접속 통제 (배포용)

마스터 토큰은 관리 기능만 지킨다. 배포하면 주소만 알아도 기사 목록은 물론 /api/analyze-url(LLM 과금) · /api/articles/{id}/telegram(발송) 까지 누구나 부를 수 있으므로, 그 앞에 세션 관문을 하나 둔다. WEB_PASSWORD(또는 마스터 패널의 '웹페이지 비밀번호')가 설정돼 있을 때만 켜지고, 비어 있으면(로컬 개발) 아무 것도 막지 않는다. 미인증이면 화면은 로그인 페이지, /api/* 는 401 이다. 통과하면 pfm_web 쿠키(HttpOnly · SameSite=Lax · 30일 · https 면 Secure)를 받는다. 세션 토큰은 저장된 비밀번호 해시에서 파생되므로 서버에 세션을 두지 않아도 재시작에 살아남고, 비밀번호를 바꾸면 기존 쿠키가 전부 무효가 된다. 잠금과 무관하게 열리는 경로는 /healthz · /api/web/* · /kakao/callback 뿐이다.
덧붙여 CORS 는 ALLOWED_ORIGINS 에 적은 주소만 허용한다(기본: 교차 오리진 차단). 수동 URL 등록은 is_public_http_url() 로 사설망·루프백·클라우드 메타데이터 (169.254.169.254) 주소를 막아 서버가 내부망을 대신 긁는 SSRF 를 차단한다.

인스턴스는 반드시 1개. run 한 프로세스 안에서 API 와 함께 수집·시세·텔레그램봇·대외협력 스레드가 돈다. 2개로 늘리면 수집·LLM·알림이 두 벌 나간다. 텔레그램은 (기사, 채널, 채팅방) UNIQUE 가 일부 막아 주지만 카카오는 막히지 않는다. 오토스케일은 최소=최대=1 로 고정한다. 자세한 절차는 DEPLOY.md.

부트스트랩 억제. 첫 실행 시각을 기록해 두고, 그 이전에 발행된 기사는 절대 알림하지 않는다. 파이프라인이 오래 멈췄다 재개될 때 과거 기사가 한꺼번에 발송되는 것을 막는다. 억제는 파이프라인이 안정될 때까지 유지되는데, 이 판정은 본문까지 확보돼 곧 분석·알림될 큐(unanalyzed_count < 30)만 본다. 메타만 저장된 넘침 기사 (deferred)는 본문·분석이 없어 알림 후보가 아니므로 억제 유지 사유에서 뺀다 — 안 그러면 배경 드레인 큐가 조금만 쌓여도 알림이 영구히 멈춘다. (2026-09-08 수정)

08 — 주간 레포트월요일 아침 이메일

한 주치 기사를 계열사·주제별로 모아 LLM이 주간 종합 SWOT과 포스코 그룹 영향 분석을 합성한다. 결과는 weekly_reports에 저장하고, 같은 HTML을 이메일과 웹 주간동향 탭이 함께 쓴다.

Gmail은 앱 비밀번호로. SMTP_USER와 앱 비밀번호는 같은 Google 계정이어야 한다. 회사 계정이 앱 비밀번호를 막으면 개인 @gmail.com을 발신자로 두고 회사 주소를 수신자로 넣는다. SWOT 4분면은 강점(초록)·약점(주황)·기회(파랑)· 위협(빨강)으로 색을 나눠 이메일에서도 한눈에 구분된다.

09 — 대외협력독립 화면 · 5개 카테고리

대외협력은 뉴스 앱과 목적·데이터가 달라 즐겨찾기 탭과 같은 방식으로 분리했다 — 헤더의 🏛 대외협력 버튼을 누르면 대외협력 화면으로 바뀌고(버튼 라벨이 ← 전체 기사로), 메인 뉴스 필터·그리드·URL등록·통계는 전부 숨는다. 독립 주소 /ea 도 유지해(@app.get("/ea")가 같은 SPA 재사용) 링크로 바로 들어올 수 있다. (뷰 전환은 요소에 hidden 을 걸어 하는데, .grid 처럼 display 를 지정한 요소는 hidden 을 무시한다 — 전역 [hidden]{display:none!important} 로 강제.)

목록은 뉴스와 같은 3열 반응형 포토카드 그리드다. 원문에 사진이 없으므로 썸네일 자리에는 카테고리 + 큰 지표를 넣는다 — 예고·의안은 D-day(마감 임박도에 따라 빨강·주황·네이비), 정책·통상 뉴스는 중요도 점수. 카드 본문은 제목·기관·기간, 그룹사·영향도 칩, 요약, 근거(AI 영향분석)·대응(초안), 원문·의견제출 버튼 순으로 쌓인다.

필터는 메인 뉴스 필터와 같은 접기식 칩 패널이되 대외협력 전용이다 (.ea-filter-panel, ea_ 접두사 쿼리). 행 구성 — 검색 · 카테고리(단일) · 기관(중복) · 영향도(중복) · 그룹사(중복) · 정렬·상태(드롭다운). 카테고리 칩이 곧 예전의 상단 탭이다: 입법·행정예고 / 국회 의안 / 정책 동향 / 통상 환경 / 부처별 동향 5개, 단일 선택. 뉴스형(정책·통상·부처별)을 고르면 영향도·그룹사· 정렬 행이 숨는다.

필터의 "언론사" 자리는 기관(정부부처·국회 상임위·KOTRA)이다. 카테고리마다 목록이 다르다 — 입법·행정예고=소관 부처(kind='ministry'), 국회 의안=소관 상임위(kind='committee'), 부처별 동향=부처, 통상 환경=KOTRA·부처, 정책 동향=기사에서 뽑은 발표 부처(제목 첫머리의 산업부,·국토부는 약칭을 정식명으로 환산). 관심 부처는 건수 0이어도 칩으로 남겨 "왜 산업부가 없지?" 혼선을 없앤다. 부처명은 매핑이 없으면 크롤 원문(agency_raw).

건수가 0인 부처가 뜨는 것과, 그 부처의 공고가 수집 자체가 안 되는 것은 다르다. 국민참여입법센터·국회 목록은 전 부처 대상으로 크롤하되 관련성 게이트(G2.5)에서 산업 키워드가 없는 일반 행정·조세·소비자 규정을 걸러낸다. 산업통상부라도 'R&D 사업관리 규정'처럼 이차전지·철강·통상과 무관한 공고는 목록에 남지 않는다.

포스코 그룹사 필터

입법·행정예고 원문에는 회사명이 나오지 않는다. 그래서 규제 대상 사업으로 그룹사를 판정한다 — 제목·법령명·분류를 EA_GROUP_RULES에 걸어 철강·환경·안전 → 포스코, 이차전지·소재 → 포스코퓨처엠, 건설·입지 → 포스코이앤씨, 통상·에너지 → 포스코인터내셔널, 스마트팩토리·AI → 포스코DX 로 태깅한다. LLM 은 쓰지 않는다 — 회사명이 본문에 없는데 모델에 맡기면 근거 없는 태깅이 대량으로 나온다(뉴스 파이프라인에서 이미 겪은 문제라 규칙이 1순위라는 원칙이 있다). 규칙만 쓰므로 비용이 0이고, 규칙을 고치면 backfill_groups로 기존 항목까지 소급 반영된다.

로직은 전부 신규 3파일(external_affairs.py · ea_crawl.py · external_affairs.{js,css})에 있고, 기존 파일에는 연결선만 그었다 — main.py 는 가드 import + 라우터 등록 + 독립 주소 @app.get("/ea")(같은 SPA 재사용), app.js 는 .filters → #mainFilters 지정 2줄(대외협력 전용 필터와 구분하기 위함), index.html 대외협력 섹션, style.css 0줄 (대외협력 필터는 style.css 의 .filters·.chip 클래스를 그대로 재사용한다). 모든 CSS 클래스는 .ea- 접두사, URL 도 경로(/ea) + ea_ 접두사 쿼리라 기존 필터 상태와 섞이지 않는다.

external_affairs.py는 main.py를 import 하지 않는다. 순환 참조를 만들지 않으려고 now_utc·iso·jload 같은 3~5줄 유틸은 복제했다. 기존 keyword_sets는 ctx.storage.enabled_keywords() 로 읽기만 하고(main.py 의 저장소 객체를 인자로 받는 것뿐, import 는 아니다), 쓰기는 ea_url_ledger에만 한다.
저장소도 DB_BACKEND 를 따른다 (2026-09-10 정비). 이전엔 이 모듈이 ctx.cfg.db_backend 값과 무관하게 항상 로컬 SQLite 파일 하나 (EaDB(ctx.cfg.sqlite_path))만 썼다 — 뉴스가 Supabase 로 넘어간 뒤에도 대외협력 5개 테이블은 계속 그 파일에만 쌓여, 저장소를 다른 PC로 복사하면 대외협력 탭만 빈 화면이 되는 문제가 있었다. 지금은 make_ea_db(ctx) 가 DB_BACKEND 를 보고 EaDB(SQLite) 또는 EaSupabaseDB (PostgREST) 를 고른다. 데이터량이 수백 건 규모라 EaSupabaseDB 는 JOIN·집계를 SQL 에 맡기지 않고 ea_policy_items·ea_agencies· ea_analyses 를 통째로 읽어 파이썬에서 조인한다(PostgREST 는 임의 JOIN 을 지원하지 않는다). 두 백엔드가 같은 메서드 이름(query_items· filters_agency_counts·item_detail 등)을 구현하므로 register_api·collect_once·주간레포트 쪽 코드는 어느 백엔드인지 모른 채 호출만 한다 — main.py 의 Storage ABC 와 같은 패턴이다. 정렬은 _ea_sort_rows() 하나로 통일해 두 백엔드의 표시 순서가 어긋나지 않는다.

게이트와 분석

뉴스와 같은 순서(G0 실행내중복 → G1 메모리캐시 → G2 DB대조 → G2.5 관련성)로 거르고, HTTP·LLM 은 G2.5 통과분에만 쓴다. 법제처에는 전 부처의 모든 법령이 올라오므로 G2.5 가 특히 중요하다 — 이차전지·철강·환경·통상 산업 관련어가 걸릴 때만 통과시키고, 나머지는 ea_url_ledger에 기록해 다음 주기에 다시 받지 않는다.

관심 부처라는 이유만으로는 통과시키지 않는다. 공정위·기재부 같은 관심 부처에서도 소비자·조세·조직 개편 같은 일반 행정 개정안이 대량으로 나오기 때문이다. 이 규칙에 구멍이 하나 있었다 — G2.5 는 뉴스 검색어(keyword_sets)를 읽기 전용으로 빌려 쓰는데, 거기에 '국토교통부' 같은 부처명이 검색어로 들어 있어 부처명만으로 통과하는 뒷문이 생겼다(실제로 '국토교통부와 그 소속기관 직제 일부개정령안'이 이 경로로 들어왔다). 지금은 빌려 온 검색어에서 ea_agencies의 이름·약칭을 빼고 쓴다.

영향도
high/medium/low/none. medium 이상은 조문 번호(안 제6조의2·제2항)나 원문 10자 이상 직접 인용이 근거에 있어야 하고, 없으면 코드가 low로 내린다 — LLM 이 근거 없이 높은 영향도를 주장하는 것을 신뢰하지 않는다. 예전에는 근거 문자열 길이만 봐서, 조문도 인용도 없이 뭉뚱그린 문장이 medium으로 통과했다.

저장하지 않는다. G2.5 통과분만 상세(REST 또는 상세 페이지 크롤)를 받아 제안이유·주요내용을 메모리로 넘겨 그 회차에 분석하고 버린다 (기존 §7-3 최소 보관과 동일). 뉴스형(부처 정책뉴스·KOTRA)은 RSS·API 가 본문을 함께 주므로 상세 HTTP 가 없다. 첫 회차에 분석을 못 한 뉴스형 항목은 다음 회차에 피드를 한 번 더 받아 본문을 맞춘다(_news_body_map). 뉴스형은 '개정이유·조문' 프롬프트 대신 '동향·시사점' 프롬프트(EA_NEWS_PROMPT)를 쓴다.
